## 2. 当前已完成基线

以下能力已经存在，不应在后续规划中重复建设：

### 2.1 skim 浏览与显示范围

- skim 复用现有主窗口壳层，不新增平行窗口状态机；
- 只读取用户当前打开目录的直接子项，不在后台递归浏览磁盘；
- 支持文件夹导航、面包屑、排序、选择、右键操作、系统打开、打开路径和原生拖出；
- 支持 `skim`、`all`、`custom` 三种持久化显示模式；
- 自定义模式支持已登记格式分类、具体扩展名和 Windows 隐藏文件开关；
- 未登记格式在全部显示模式下可使用通用图标和文件信息预览。

### 2.2 多格式目录层与基础搜索

- 中央格式能力表已经区分浏览、正式索引、正式搜索、缩略图、预览类型与 AI 能力；
- 已登记的非视觉格式可以进入已添加目录的通用文件目录层；
- 非视觉文件可按文件名和扩展名参与现有基础搜索；
- 非视觉条目不会被误计为未识别图片，也不会进入视觉 AI 任务。

### 2.3 当前缩略图和预览

- 14 种现有视觉格式继续使用 Cap7CE 自有代表图、缩略图和预览缓存链；
- skim 使用独立的 `skim-cache/thumbnails`、`previews` 和 `metadata`；
- skim 只为当前视口及邻近区域按需请求缩略图，离开目录后停止领取新任务；
- 显式空格预览优先于缩略图后台队列；
- 已支持视觉内容、文件/文件夹信息、TXT/MD 文本、MP3/WAV 音频和 MP4/MOV 视频预览；
- 不支持解析或播放的内容回退到文件信息预览。

## 4. 工作流 A：Windows / 第三方缩略图

### 4.1 目标

当资源管理器已经能够显示某个文件的缩略图时，Cap7CE 尽量按需取得同一类结果，而不是为每种专有格式自行编写解析器。

典型目标包括：

- 安装 KeyShot 后由系统显示缩略图的 `.ksp`；
- Office、WPS 或其他软件注册缩略图处理器的文档；
- 系统或解码器能够提供代表图的视频、RAW、CAD、3D 和工程文件；
- Cap7CE 尚未建立原生渲染器，但 Windows Shell 已有可用结果的格式。

### 4.2 已确认的技术入口

当前项目使用 Electron 43，类型定义中存在：

```ts
nativeImage.createThumbnailFromPath(path, size)
```

该接口支持 Windows，并且 Cap7CE 当前的视觉渲染服务已经在特定格式路径中调用它。因此首轮不应直接规划 Node 原生扩展、COM 桥接或独立辅助进程，而应先验证现有 Electron API 是否会调用 Windows Shell 已注册的缩略图处理器。

只有满足以下任一条件时，才进入原生桥接备选方案：

- Electron API 无法取得资源管理器中实际可见的第三方缩略图；
- 调用无法合理超时或隔离，第三方处理器会明显阻塞主进程；
- 无法区分有效缩略图与无意义的通用文件图标；
- 必须取得 Electron API 未暴露的 Windows Shell 标志、缓存策略或来源信息。

### 4.3 不采用直接读取 Explorer 缓存文件

首选方案不是直接解析 `%LOCALAPPDATA%\Microsoft\Windows\Explorer` 下的 `thumbcache_*.db`，原因包括：

- 缓存键、数据库格式和淘汰策略属于 Windows 内部实现，不是稳定的应用契约；
- 很难可靠地从任意源路径映射到缓存条目；
- 缓存可能没有目标尺寸、已经失效或尚未生成；
- 直接读取不能替代调用已注册的第三方缩略图处理器；
- Windows Shell API 本身可以决定复用缓存还是调用处理器。

因此产品语义应称为“使用系统缩略图能力”，而不是“读取系统缩略图数据库”。

### 4.4 建议的缩略图优先级

```text
Cap7CE 已有原生视觉渲染器
  -> Windows Shell / 第三方缩略图
  -> 对应格式专用图标
  -> 通用文件图标
```

约束：

- 不用 Shell 结果覆盖 Cap7CE 已经稳定支持的高质量视觉渲染；
- Shell 缩略图只改变显示能力，不自动改变 `canIndex`、`canSearch`、`canAIIndex`；
- Shell 返回空图片、错误、超时或疑似无意义结果时立即回退格式图标；
- 首期只用于 skim，不同步扩大正式搜索结果页的缩略图范围；
- 是否扩展到正式搜索结果应在 skim 运行稳定后另行确认。

### 4.5 调度与资源约束

系统缩略图同样必须遵守当前低占用原则：

- 仅在用户进入目录且条目进入当前视口或邻近预取范围后请求；
- 不因启动软件、加载已添加目录列表或进入后台而请求；
- 不递归为未打开目录生成缩略图；
- 使用低并发，首轮建议串行或最多 2 个并发；
- 离开目录、退出 skim 或主窗口进入后台后停止领取新任务；
- Electron 调用若无法真正取消，使用会话代次忽略迟到结果；
- 单个第三方处理器超时不得阻塞后续整个目录；
- 不执行源文件，不主动启动对应桌面软件，不触发 AI。

### 4.6 缓存策略

成功取得的 Shell 缩略图写入 skim 自有缓存，不直接依赖 Explorer 缓存持续存在。

缓存身份至少包括：

- 规范化源路径；
- 文件大小；
- 精确修改时间；
- 目标缩略图规格；
- Cap7CE 缓存版本；
- 渲染来源，例如 `native` 或 `shell`；
- Shell 缩略图策略版本。

缓存失效规则继续复用当前源文件大小、修改时间和内部版本策略。不能因为 Shell 缩略图接入而增加启动时全盘核对。

### 4.7 第一轮可行性样本

原型测试应覆盖“成功、失败、无处理器、处理器异常”四类情况。建议使用以下样本：

| 类别 | 样本 | 验证目标 |
| --- | --- | --- |
| 第三方项目 | `.ksp` | KeyShot 已安装时能否取得与资源管理器相近的代表图 |
| Office | `.docx`、`.xlsx`、`.pptx` | 系统或 Office 处理器是否返回内容缩略图 |
| 视频 | `.mp4`、`.mkv` | 不同系统解码能力下的覆盖差异 |
| 专业影像 | `.dng`、至少一种相机 RAW | 系统扩展存在与不存在时的行为 |
| 3D / CAD | `.blend`、`.skp` 或 `.dwg` | 第三方处理器注册差异 |
| 无处理器格式 | 任意未知扩展名 | 快速失败并稳定回退通用图标 |
| 损坏文件 | 损坏的测试副本 | 不崩溃、不持续重试、不阻塞队列 |

测试时应同时记录：

- 资源管理器是否显示真实缩略图；
- Electron API 是否返回非空图片；
- 首次调用与缓存后调用耗时；
- 是否启动关联软件或产生额外进程；
- 后台、退出目录和快速滚动时是否继续占用 CPU / 磁盘；
- 第三方软件卸载或缩略图处理器失效后的回退行为。

### 4.8 第一轮通过标准

只有同时满足以下条件，才进入正式接入：

- `.ksp` 或至少一种第三方注册格式能取得有效缩略图；
- 无处理器和损坏文件可以快速、安全回退；
- 快速滚动和切换目录不会显示迟到的错误条目；
- 后台和未浏览状态不产生持续缩略图任务；
- 不改变正式索引、AI 和现有视觉缩略图行为；
- 开发版构建、集成测试和手动资源占用观察通过。

## 5. 工作流 B：更多内容预览 Provider

### 5.1 当前边界

当前明确支持：

- 图片及现有视觉代表图；
- TXT / MD 文本；
- MP3 / WAV 音频；
- MP4 / MOV 视频；
- 其他文件和文件夹的信息预览。

缩略图和内容预览必须继续分开：能够取得系统缩略图，不代表 Cap7CE 能够安全打开、分页、播放或解析该文件。

### 5.2 建议优先级

#### B1：低风险文本与结构化数据

候选格式：

- JSON、XML、YAML、YML；
- CSV；
- RTF 的纯文本降级；
- HTML 的源文本或安全提取文本。

约束：

- 限制最大读取字节数；
- 检测 BOM 和常见文本编码；
- 不执行 HTML、脚本、宏或外部资源；
- 解析失败回退文件信息。

#### B2：更多音视频格式

候选格式：AAC、FLAC、M4A、OGG、WEBM、M4V 等。

实施前必须逐项验证当前 Electron / Chromium 实际解码能力，不能仅根据 Windows 默认播放器能够播放就声明支持。无法原生播放时继续使用系统打开和文件信息预览，不为首期引入大型转码依赖。

#### B3：字体与压缩包

- 字体：可考虑显示字体名称、样式和受控示例文本；
- 压缩包：可考虑只读条目列表、总数量和解压后估算信息；
- 不自动解压，不运行压缩包内容，不为预览写入源目录。

#### B4：Office、WPS、OpenDocument 与 EPUB

需要先区分两类目标：

1. Shell 缩略图：只显示封面或首屏代表图；
2. 内容预览：提取文本、分页或高保真渲染。

首期优先 Shell 缩略图；高保真 Office 预览涉及组件依赖、兼容性、安全和体积，必须另开技术评估。不得把“已安装 Office 可打开”直接等同于“Cap7CE 可以内嵌预览”。

#### B5：RAW、CAD、3D 与专有工程文件

首期策略：

- 优先尝试 Shell / 第三方缩略图；
- 空格预览仍可先显示放大的系统代表图或文件信息；
- 不承诺 3D 交互、图层、时间线、材质或工程结构解析；
- 只有真实用户需求明确且依赖许可可接受时，才为单一格式增加专用 Provider。

### 5.3 每个 Provider 的准入条件

每增加一种内容预览类型，应分别确认：

- 文件签名与扩展名不一致时的处理；
- 最大文件大小和读取上限；
- 取消、切换项目和关闭窗口后的资源释放；
- 编码、损坏文件和不支持内容的回退；
- 是否产生临时文件以及退出后的清理；
- 是否增加安装包体积、原生依赖或许可证要求；
- 是否会在后台继续播放、解码或扫描；
- 中英文提示与错误文案。

## 6. 工作流 C：未登记扩展名的自定义规则

### 6.1 当前状态

当前“自定义 skim”主要配置中央能力表已经登记的格式。全部显示模式能够显示未知格式，但用户尚不能手动输入一个未登记扩展名并持久设置为始终显示或始终隐藏。

### 6.2 暂定方案

如果真实使用中出现需求，可在现有设置区域增加低频入口：

- “始终显示”扩展名列表；
- “始终隐藏”扩展名列表；
- 输入时统一转为小写并补齐前导点；
- 拒绝路径、通配符、空字符串和非法文件名字符；
- 同一扩展名不能同时位于显示与隐藏列表；
- 文件夹始终显示，不受扩展名规则影响；
- Windows 隐藏文件开关保持独立，优先级需在实施前确认。

建议优先级：

```text
Windows 隐藏属性规则
  -> 用户“始终隐藏”
  -> 用户“始终显示”
  -> 当前 skim / all / custom 模式规则
```

该优先级目前只是建议，开始实现前需要再次确认。

### 6.3 暂缓理由

- 全部显示已经提供完整兜底；
- 当前登记范围已覆盖主要用户文件；
- 增加自由输入会引入校验、冲突、导入导出和错误恢复问题；
- 应先收集真实缺失格式，再决定是否值得增加界面复杂度。

## 7. 工作流 D：搜索增强大版本

搜索增强继续与缩略图、预览 Provider 分离，不作为上述工作的前置条件。

暂缓内容包括：

- 文档正文提取和全文搜索；
- OCR；
- 父级目录、路径和文件夹语义；
- 文件元数据、正文、OCR、AI 描述等多来源证据；
- 查询权重、相关性排序与可解释匹配；
- 模型辅助索引或查询理解；
- 适配当前 `sql.js` / FTS3 能力的索引设计或后续数据库迁移。

启动条件：

1. skim、系统缩略图和当前多格式预览链稳定；
2. 收集真实的无结果、误命中和难定位案例；
3. 明确首期只解决哪一类搜索问题；
4. 单独评审数据库、索引迁移、后台任务和回退策略；
5. 使用独立版本和独立提交实施。

详细研究方向继续参考 `SEARCH_ENHANCEMENT_RESEARCH_PLAN.md`。

### 第 3 轮：低风险内容预览扩展

内容：

### 第 5 轮：任意扩展名自定义规则

仅当用户确实经常需要未登记格式时实施。开始前重新确认设置页布局、优先级和数据结构。

### 独立大版本：搜索增强

不与第 1 至第 5 轮混合。按 `SEARCH_ENHANCEMENT_RESEARCH_PLAN.md` 重新立项。

## 9. 通用测试矩阵

后续缩略图或预览轮次至少覆盖：

### 9.1 功能

- 有处理器、无处理器、损坏文件和零字节文件；
- 中文、英文、空格、超长路径和特殊字符文件名；
- 本地盘、可移动盘和断开后的路径；
- 快速滚动、连续切换目录、连续空格预览；
- skim / all / custom 三种显示模式；
- 缓存命中、缓存失效和清理后重建。

### 9.2 生命周期

- 退出当前目录后不再领取任务；
- 退出 skim 后不显示迟到结果；
- 主窗口后台、standby 和关闭时停止新任务；
- 预览关闭后释放媒体、文件句柄和临时数据；
- 关联软件卸载或处理器失效后正常回退。

### 9.3 资源

- 未浏览磁盘时不主动访问对应磁盘；
- 后台不持续产生 CPU 或磁盘活动；
- 大目录只处理视口及邻近范围；
- 失败格式不在同一会话内无限重试；
- 缓存统计只在用户打开相关设置时读取；
- 不新增启动时全盘扫描。

### 9.4 回归

- 现有视觉缩略图、预览和 AI 能力不变；
- 正式搜索结果和 skim 缓存继续隔离；
- 主窗口与预览窗口状态机不变；
- 文件打开、拖出、打开路径和右键菜单不变；
- `npm run build`、`npm test` 与 `git diff --check` 通过；
- 视觉和交互由用户手动确认。

## 11. 当前推荐下一步

下一项建议只执行“第 1 轮：Shell 缩略图可行性原型”。

理由：

- 它直接验证 `.ksp` 等第三方软件缩略图能否复用；
- 当前 Electron 已有候选 API，试验成本明显低于原生扩展；

- 原型不接入正式 UI，失败时不会影响现有稳定行为；
- 可以在扩展预览范围之前，先获得最有价值的可视化提升。
