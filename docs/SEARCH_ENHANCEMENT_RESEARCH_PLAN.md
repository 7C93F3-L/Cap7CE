# Cap7CE 搜索系统增强研究规划

> 文档状态：暂缓实施，作为 skim 与多格式链路稳定后的独立大升级
> 基线版本：0.7.8
> 更新日期：2026-08-03
> 当前动作：保留构想、积累样本，不修改正式搜索架构
> 后续承接：启动条件与当前优先级统一参考 `REMAINING_CAPABILITY_ROADMAP.md`

## 1. 文档目的

本文独立记录 Cap7CE 关于路径语义、目录关联、文档全文、OCR、多来源证据和模型辅助搜索的构想、可行边界与后续研究流程。

本方向不再作为 skim 和多格式接入的前置条件。当前先完成：

1. skim 基础浏览与目录添加；
2. 多格式文件在 skim 中的浏览、打开、打开路径和拖出；
3. 白名单多格式文件接入已添加目录和现有基础搜索；
4. 非视觉内容预览与 skim 独立缓存。

待上述交互跑通并积累真实使用中的无结果查询、误命中和难定位案例后，再将搜索增强作为独立大版本设计和实施。

## 2. 暂缓原因

最初的“路径语义搜索”设想主要是：

- 已添加根目录名称参与搜索；
- 根目录以下各级相对目录名称参与搜索；
- 文件名和扩展名参与搜索；
- 多个查询词可以分别命中不同字段。

继续讨论后，目标已扩展为：

- 父级和子级路径名称；
- 同目录多数文件名的公共信息；
- 无意义目录名称下的项目关联推导；
- 文档正文搜索；
- 图片和扫描文档 OCR；
- 视觉内容理解；
- 多项证据汇总后再按查询条件判断；
- 代码规则困难时使用本地语言或视觉语言模型辅助。

这已不是一次局部 SQL 调整，而是一套多来源搜索证据系统。如果在 skim、多格式文件模型和真实使用流程尚未稳定前确定数据库与查询结构，后续很可能因为新增文档、OCR 和模型来源而再次迁移或重构。

因此当前暂停编码，不把未经验证的推断逻辑提前写入正式索引。

## 3. 后续总体方向

搜索增强建议拆成三层，确保添加目录后仍能立即使用，并允许结果随后逐步丰富。

### 3.1 即时索引

添加目录或发现文件后立即得到，不依赖 OCR 或模型：

- 文件名；
- 文件扩展名；
- 已添加根目录真实名称；
- 用户修改后的目录显示名称；
- 根目录以下各级相对目录名称；
- 文件大小、修改时间和格式；
- 同目录文件名的高频公共片段；
- 代码可以稳定提取的项目编号、版本号或名称片段。

即时索引负责首次添加目录后的基础可搜索性，不应等待后台深度处理。

### 3.2 后台内容索引

按格式和能力逐步补充：

- TXT、MD、JSON、XML、YAML、CSV、HTML 等文本；
- DOCX、PPTX、XLSX 等容器内的可提取文本；
- PDF 自带文字层；
- 无文字层的 PDF、扫描文档和图片 OCR；
- 可安全读取的文件元数据。

后台内容索引必须：

- 增量执行；
- 可暂停和取消；
- 限速并避免拖慢系统；
- 记录源文件大小、精确修改时间和提取器版本；
- 文件未变化时不重复处理；
- 失败不阻止基础搜索；
- 不因启动软件自动全盘处理。

### 3.3 可选 AI 深度索引

只处理代码规则和专用提取器难以覆盖的场景：

- 视觉内容描述；
- 复杂版面和低质量文字；
- 目录与文件之间可能存在的项目关联；
- 用户命名全部无意义时的内容概括；
- 其他需要概率判断的弱语义。

AI 结果是搜索证据之一，不应覆盖或伪装成：

- 人工关键词；
- 文件原文；
- 路径原文；
- OCR 原文；
- 确定性的文件元数据。

模型任务优先在索引阶段运行并保存结果，不应在每次查询时临时分析大量文件。

## 4. 搜索证据模型

后续不建议把所有文本简单拼成一个大字段。每项证据应保留：

- 来源类型；
- 原始值或规范化值；
- 关联文件或目录；
- 置信度；
- 生成方式；
- 提取器或模型版本；
- 源文件状态；
- 更新时间和失效依据。

建议的初步可信级别：

| 证据来源 | 初步定位 |
| --- | --- |
| 人工关键词 | 最高可信 |
| 文件名、扩展名、直接路径 | 高可信 |
| 文档原文精确命中 | 高可信 |
| 目录内公共名称推导 | 中等可信 |
| OCR 文字 | 中等可信 |
| AI 描述、关键词或目录意图 | 辅助可信 |

查询可以将词拆分后分别匹配不同来源。

例如已添加：

`D:\产品\DSD16`

文件位于：

`D:\产品\DSD16\2026\D09\详情页\abc123.psd`

查询 `DSD16 详情页` 时：

- `DSD16` 可以由根目录或父级路径命中；
- `详情页` 可以由子目录、文件名、文档正文、OCR 或 AI 描述命中；
- 两个词不必来自同一个字段；
- 最终结果应能够说明各查询词由什么证据命中。

这种可解释性既方便用户理解，也方便排查误命中。

## 5. 各构想的可实现程度

### 5.1 确定可实现

- 已添加根目录和相对路径参与搜索；
- 父级、子级目录名称参与搜索；
- 文件名、扩展名和基础元数据；
- 多词跨来源 AND 判断；
- 常见文本和文档内容提取；
- PDF 文字层读取；
- 专用 OCR 后台任务；
- 现有视觉模型生成描述和关键词；
- 将不同来源分开保存并汇总判断。

### 5.2 可以实现，但必须用真实样本验证

- 从同目录多数文件名中推导公共项目名称；
- 判断某个无意义目录属于哪个项目；
- 自动过滤通用词、流水号和无意义编号；
- 相关性排序和来源权重；
- OCR 与视觉描述的可信度；
- 小模型对中文产品图、详情页、设计稿和复杂文档的理解；
- 将 AI 推导词传播给同目录或关联文件。

### 5.3 无法保证可靠

- 在路径、文件名和内容均无意义时必然正确理解用户意图；
- 仅凭少量文件稳定推断整个目录用途；
- 用一个固定阈值适配所有用户的目录习惯；
- 让语言模型代替全部代码规则、OCR 和文档解析；
- 将模型输出当作确定事实而不保留来源和置信度。

这些能力可以提供辅助命中，但不能承诺无误。

## 6. 目录公共信息的代码分析方向

同目录或关联目录的文件名可以先使用确定性方法分析：

- 去除扩展名；
- 按空格、连接符、下划线、大小写边界和数字边界切分；
- 提取公共前缀、后缀、词组和字符片段；
- 统计词或片段在有效文件中的出现比例；
- 设置最少样本数；
- 过滤纯序号、日期、分辨率、版本号和常见无意义词；
- 区分文件自身名称与由同目录推导出的弱证据；
- 目录变化后增量重算；
- 保存推导依据，允许后续调整规则版本。

例如只有某个词在足够多的有效同级文件中出现，才可成为目录级候选证据。小目录、混合项目目录和通用命名需要降低置信度或不推导。

在建立真实样本前，不提前确定统一百分比和最少数量。

## 7. 文档全文与 OCR

全文搜索首先应使用专用格式解析和 OCR，而不是默认调用视觉语言模型。

建议顺序：

1. 直接读取文本格式；
2. 提取 Office 容器和 PDF 文字层；
3. 仅对没有可用文字层的页面或图片执行 OCR；
4. 只有复杂视觉语义无法由 OCR 表达时，才进入视觉模型。

当前项目使用的 `sql.js` 已实测启用 FTS3，但没有 FTS5。因此中文全文搜索仍然可做，但需要在正式设计时比较：

- FTS3 与自定义分词；
- 中文字符或 n-gram 索引；
- 独立内容表和分块策略；
- 有限规模下的普通字段查询；
- 是否需要更换或定制 SQLite 构建。

在测试真实文档数量、数据库体积和中文查询效果前，不提前锁定实现。

## 8. 模型方向

当前默认方向为 `Qwen3-VL-4B-Instruct-Q4_K_M`。后续可以将 `Qwen3-VL-2B-Instruct` 纳入真实样本对比。

官方 2B GGUF 大致包括：

- Q4_K_M 主模型约 1.11 GB；
- Q8 mmproj 约 445 MB；
- F16 mmproj 约 819 MB。

官方 4B Q4_K_M 主模型约 2.5 GB。模型文件大小不等于实际 RAM 或显存占用，仍需计算 mmproj、上下文、KV 缓存、GPU 层数和运行后端。

规格参考（2026-07-30 核对）：

- [Qwen3-VL-2B-Instruct-GGUF](https://huggingface.co/Qwen/Qwen3-VL-2B-Instruct-GGUF/tree/main)
- [Qwen3-VL-4B-Instruct-GGUF](https://huggingface.co/Qwen/Qwen3-VL-4B-Instruct-GGUF/tree/main)

模型生命周期建议：

- 不默认永久常驻；
- 有识别或深度索引任务时加载；
- 空闲一段时间后卸载；
- 未来可以提供“保持模型运行”选项；
- 搜索输入本身不应触发批量模型分析；
- 2B 与 4B 使用同一批真实文件比较速度、内存、中文 OCR、描述质量和关键词稳定性。

截至本文整理时，未确认存在官方 Qwen3-VL 低于 2B 的正式版本。第三方更小模型不作为默认路线，除非后续完成许可证、运行时、性能和质量验证。

如果未来目标主要是跨模态检索，也可以研究专用视觉/文本 embedding 或 reranker，而不是始终使用生成式 VL 模型；但这可能引入当前 llama.cpp 路线之外的新运行时，不能提前视为既定方案。

## 9. 与 skim 和多格式的关系

先完成 skim 与多格式并不是绕开搜索，而是在建立搜索增强需要的基础：

- 通用 drive / folder / file 条目；
- 中央格式能力表；
- 文件格式白名单；
- 已添加目录中的通用文件记录；
- 非视觉文件与视觉 AI 任务的边界；
- 文本、文档、媒体和视觉预览 Provider；
- 可取消、可限速的文件处理任务；
- 用户真实的目录添加和定位流程。

多格式进入正式搜索时，首期只沿用现有基础搜索能力。不得因为预留未来搜索升级而提前加入：

- 路径意图推断；
- 目录聚类；
- 全文索引；
- OCR；
- embedding；
- AI 目录分析；
- 新相关性排序。

底层类型可以保留扩展入口，但当前不展示空壳功能。

## 10. 后续研究流程

正式启动搜索大升级前，先准备小型真实评测集。

建议至少包含：

- 若干真实目录树；
- 有意义和无意义的目录名称；
- 有规律和无规律的文件名；
- 同目录单项目与混合项目；
- 文本、Office、PDF、扫描件和图片；
- 中英文及混合命名；
- 期望命中的查询；
- 不应命中的反例；
- 当前搜索失败原因。

研究顺序：

1. 记录真实无结果和误命中案例；
2. 建立可重复运行的查询样本；
3. 先实现独立于正式数据库的代码原型；
4. 比较仅文件名、路径增强、目录公共词、正文、OCR 和 AI 各层增益；
5. 记录准确率、误命中、索引耗时、数据库体积、内存和模型成本；
6. 再决定正式字段、索引结构、迁移和查询规则；
7. 将搜索增强拆成独立版本和独立提交。

## 11. 暂定升级阶段

以下仅是研究顺序，不是当前执行轮次：

1. 搜索证据数据模型与评测集；
2. 文件名和路径确定性证据；
3. 同目录公共信息推导；
4. 文档正文提取与全文索引；
5. OCR 后台索引；
6. 可选 AI 深度索引；
7. 多来源汇总、相关性和可解释命中；
8. 数据迁移、性能与真实使用验证。

任一阶段都应允许用户在深度索引尚未完成时继续使用即时基础搜索。

## 12. 当前结论

当前不开始搜索增强代码工作。

近期执行入口改为：

`docs/SKIM_MULTI_FORMAT_EXECUTION_PLAN.md`

等 skim、多格式、预览和已添加目录基础链路稳定后，再根据真实使用结果重新讨论本文，并决定是否进入独立搜索大版本。
